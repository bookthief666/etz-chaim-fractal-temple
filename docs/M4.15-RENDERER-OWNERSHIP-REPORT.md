# M4.15 — Renderer Ownership & Realm Isolation

Runtime: `m4.15.0`  
Implementation source: exact M4.14 archive from the supplied audit bundle  
Physical stability baseline: M4.10, accepted by the owner on Samsung Galaxy Z Fold 6

## Regression history

### M4.10 → M4.11 — Living Tree Instrument

Confirmed source changes:

- The realm, path-metamorphosis, sacred-geometry, palette, and realm-kernel shader files are byte-for-byte unchanged.
- One new `useFrame` callback was added: `TreeInstrumentField`.
- Two existing callbacks gained work:
  - `Sephirah.useFrame` began animating a focused numerical crown and number ring and applying graph-neighbour resonance.
  - `PathSegment.useFrame` began advancing two additional path-current motes.
- New Three/R3F scene objects:
  - `TreeInstrumentField`: three pillar boxes; three principal rings; two cross-lines; two pulse toruses.
  - Focused Sephirah: `node.number` bead spheres and a number-ring torus.
  - Connected/selected paths: two additional mote spheres.
- New React computation/subscription work:
  - `TreeOfLife.useMemo` derives the graph-aware `resonantIds` set.
  - `App.useMemo` derives focused node degree.
  - No new external state subscription and no new `useEffect` were introduced by M4.11.
- New DOM/compositor behavior:
  - Tree/path focus classes, title/copy/mode transitions, aurora/shimmer focus transforms, threshold-sigil filter transitions, and a blurred invocation-margin light wash.
  - These additions are scoped to Tree focus; M4.11 added no new CSS keyframe definition.
- Lifecycle evidence:
  - The macro Tree and all M4.11 additions remained mounted during M4.11's Tree, ingress, and return states.
  - They unmounted in realm and path states. M4.11 therefore did **not** leave the Living Tree Instrument rendering behind a seated realm, but it did raise the CPU/GPU object and animation load immediately before realm entry and during return.

Conclusion: the unchanged realm shader rules out a direct M4.11 shader edit. It does not rule out runtime pressure from the enlarged macro scene, ingress overlap, browser compositor state, shader compilation, or lifecycle behavior.

### M4.11 → M4.12 — Motion-safe descent and complete path lens

Confirmed source changes:

- `useFractalNavigation` added a second realm/path `useFrame` owner: a bounded input governor with a `0.72` maximum queue, `2.15` active speed, `1.45` coast speed, and clamped coalesced pointer/wheel deltas. Raw events stopped changing shader depth directly.
- Realm/path quality adaptation began reserving headroom for gesture velocity/energy and recursive-stage boundaries.
- The Study lens expanded to all 22 documentary paths while retaining only two traversable mathematical operators.
- Connected paths gained R3F `Html` inscriptions; the lens gained additional DOM animation and documentary rendering.
- Tree first-light and recovery code did not change between M4.11 and M4.12. The M4.10-era first-light watchdog model therefore remained in force.

### M4.12 → M4.13 — Deterministic first light

Exact watchdog change:

- Removed `treeBootWatchdog` / `treeBootRetries`, which automatically remounted the Canvas after 4.2 seconds without first light.
- Added a 9-second `treeStallTimer` that only reveals a user-operated retry action; the timer itself does not remount.
- Tree readiness changed from seven R3F frames to two frames followed by a presentation `requestAnimationFrame`.
- First paint became DPR 1. Stars, astrolabe, numerical crowns, path inscriptions/motes, and OrbitControls wake 180 ms after an actual Tree-ready signal.
- Realm shaders and navigation were unchanged from M4.12.

Conclusion: M4.13 genuinely removed a destructive automatic first-light remount and reduced first-paint work. It did not establish that every browser could create/retain a WebGL context; it improved one failure mechanism rather than proving first-light reliability universally.

### M4.13 → M4.14 — Tiphareth fast path and browser policy

Confirmed source changes:

- Tiphareth gained a dedicated fragment program preserving its hexagram, sixfold court, recursive corridor, glyph field, and stage/epoch grammar.
- Architecturally it follows Malkuth: a realm-specific raymarch program imports shared sacred-geometry and palette modules and removes runtime `uRealmKind` dispatch.
- Malkuth remains a dedicated mineral/crystal program; Tiphareth is a distinct solar program rather than a copied Malkuth composition.
- The other eight realms still used the giant shared `realmFragmentShader` with the entire `realmKernelsGLSL` dispatcher.
- Approximate interpolated shader-source pressure measured during audit:
  - shared eight-realm program: about 40 KB;
  - dedicated Tiphareth: about 15.5 KB;
  - dedicated Malkuth: about 16.1 KB.
- `ShaderPrewarmer` expanded its queue from Malkuth/shared realm/path to Malkuth/Tiphareth/shared realm/path.
- It used `compileAsync` only with `KHR_parallel_shader_compile`, but cancellation was cooperative JavaScript state checked after an awaited compile. An in-flight WebGL compilation could not actually be cancelled and could overlap ingress or the first frames of a requested realm.
- DuckDuckGo detection disabled prewarm and selected a quieter context policy, but other browsers retained the expanded queue.

Conclusion: M4.14 reduced Tiphareth's individual compiler surface but retained shared-compiler pressure for eight realms and expanded speculative work elsewhere.

## Confirmed causes, suspects, and unknowns

### Confirmed engineering causes removed in M4.15

- Speculative GPU compilation had no hard cancellation boundary and could survive a phase change.
- Eight realm identities compiled through one large runtime-dispatched fragment program.
- `TempleAtmosphere` removed blur during realm/path but continued full-viewport keyframe animations and blend-mode recomposition for aurora, shimmer, rings, and ten marginal glyphs.
- Renderer recovery authority was fragmented across first-light delay, entry seating, and WebGL recovery paths. Context loss could remount the Canvas and mutate navigation phase instead of preserving the current rite.
- The old runtime phase vocabulary mixed UI transition states and renderer ownership without one exported ownership contract.

These are source-confirmed runtime pressure/lifecycle defects. The supplied archives and container cannot prove which one physically produced each Fold glitch.

### Strong causal suspects

- M4.11's larger macro scene increased work immediately before entry, making overlap with later shader compilation more costly even though it did not remain mounted in a seated realm.
- Shared-program compilation plus animated compositor layers could create burst pressure on Samsung Chromium-class mobile GPUs.
- Immediate Canvas remount during context loss could interfere with the browser's restoration of the lost canvas and could present as an involuntary return or blank frame.

### Still unknown

- Whether the Fold failures were shader compile timeout, context loss, compositor starvation, thermal/DVFS response, browser-process eviction, or a combination.
- Whether dedicated Tiphareth itself glitched because of GLSL execution cost, compilation overlap, recovery behavior, browser context policy, or non-WebGL compositor load.
- Physical Samsung Internet, Chrome, DuckDuckGo, Fold thermal, and Quest/WebXR behavior remains unverified in this environment.

## Architecture before / after

| Concern | M4.14 | M4.15 |
|---|---|---|
| Runtime phases | Ad hoc lowercase Tree/entering/fractal/path/returning plus separate threshold visibility | One `THRESHOLD / TREE / INGRESS / REALM / PATH / RETURN` model |
| Tree ownership | Tree rendered behind threshold and during ingress/return | Accepted DPR-1 Tree core remains pre-seated in THRESHOLD; Tree remains visible in TREE/INGRESS/RETURN and never runs in REALM/PATH |
| Realm ownership | Static shared/dedicated switch in `FractalRealm` | REALM-only lazy registry; one requested program mounted |
| Shader dispatch | Dedicated Malkuth/Tiphareth; giant shared program for eight | Ten dedicated program identities; eight generated from shared primitives and selected kernels |
| Shader preparation | Speculative `compileAsync` queue | No speculative WebGL compile; requested dynamic module loads on explicit entry, material compiles only when REALM owns it |
| Atmosphere | Animated viewport layers through every phase | Full animated design in Threshold/Tree/Ingress/Return; visually retained static compositor plate in Realm/Path |
| Recovery | First-light delay, entry watchdog, context handler, and remount logic had separate authority | Reducer lifecycle: healthy → entering → running → context lost → restoring → restored or failed |
| Context loss | Phase mutation and Canvas remount | Actual WebGL signals only; preserve phase/selection/depth; restore existing canvas; deliberate reseat only after failure/user action |
| QA | No physical-test report surface | `?qa=1`, live overlay, browser/GPU/frame/lifecycle counters, COPY QA REPORT, automation API |

## Realm sharding

- `realmRegistry.js` is the only dispatch authority and uses one dynamic import per Sephirah.
- Malkuth and Tiphareth retain their audited dedicated source files.
- Kether, Chokmah, Binah, Chesed, Geburah, Netzach, Hod, and Yesod receive dedicated generated programs.
- `createRealmProgram.js` shares math, SDF primitives, palette functions, raymarch infrastructure, and the source-critical realm-kernel library, then selects only the requested DE/glyph/line composition.
- Every instantiated realm fragment was verified to omit `uRealmKind`; no program sent to WebGL contains the ten-way realm dispatcher.
- Measured instantiated fragment sizes range from about 14.3 KB to 16.4 KB for all ten realms, rather than the approximately 40 KB shared M4.14 program.

## Fold QA procedure

1. Install dependencies with `npm install`.
2. Run `npm run build` and serve `dist` over HTTPS or the established no-cache QA server.
3. Open the build with `?qa=1`.
4. Traverse Tree → each realm → several depth stages → return; traverse both operative paths.
5. Use **COPY QA REPORT** after any glitch and after a complete clean circuit.
6. Record browser name/version, Fold posture, thermal state if known, and whether the event was visual corruption, blank frame, context loss, return-to-Tree, or input stall.

No physical acceptance is claimed by M4.15.
